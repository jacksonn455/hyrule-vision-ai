# Dataset

Images are **not** committed to git (size and copyright). Only this folder skeleton is versioned.

```
data/
├── inbox/               # 0. Drop images you collected by hand here (see "Importing images by hand")
│   ├── <label>/<subcategory>/
│   └── sprite-sheets/<label>/<subcategory>/
├── raw/                 # 1. Collected images, one folder per class, one sub-folder per game / kind
│   ├── link/            #    nes, a-link-to-the-past, ocarina-of-time, majoras-mask, wind-waker,
│   ├── zelda/           #    twilight-princess, skyward-sword, breath-of-the-wild, tears-of-the-kingdom, unspecified
│   └── other/           #    ganondorf, one folder per named character (midna, skull-kid, mipha, saria, malon…),
│                        #    enemies, npcs, creatures, objects, other-characters (characters without a folder)
├── sources/sprite-sheets/   # original sprite sheets (frames cut from them live in raw/)
├── metadata/
│   ├── sources.json     #    origin, license, attribution, official/fan-made and SHA-256 of every image in raw/
│   ├── rejections.json  #    every refused image and why
│   ├── review-notes.json    # findings of the visual review (shown in the report)
│   └── imports/         #    one summary per manual import
├── cache/               #    downloaded archives and extracted frames (safe to delete)
└── dataset/             # 2. Generated by `npm run ml:split-dataset` from raw/ (never edit by hand)
    ├── characters/{train,validation,test}/{link,zelda,midna,…,other}/  + classes.json
    └── games/{train,validation,test}/{breath-of-the-wild,wind-waker,…}/ + classes.json
```

The **character is the first folder** under `raw/` (`raw/midna/` = Midna). A character folder with at least 10 images
becomes a class of the character model; smaller ones are merged into `other`. For Link and Zelda the sub-folder is the
**game**, which trains the game model (`unspecified` = the source does not say which game, and is ignored there).
**Sheik is not part of `zelda`** in this first experiment (see `docs/research/IMAGE-SOURCES-RESEARCH.md`).

## Collecting images automatically

```bash
npm run ml:collect-dataset -- --dry-run      # plan only: candidates per class and sub-category
npm run ml:collect-dataset -- --target 300   # download (resumable: run again to continue / retry)
npm run ml:review-dataset -- sheets          # contact sheets in data/review/ for a visual check
npm run ml:review-dataset -- reject --reason "two characters" data/raw/link/...jpg
npm run ml:dataset-report                    # docs/research/DATASET-COLLECTION-REPORT.md
npm run ml:sync-metadata                     # after moving/renaming/deleting files in raw/ by hand
npm run ml:reorganize-raw -- --only-from other-characters   # re-file images after the folder rules change
```

You can organise `raw/` by hand (move, rename, delete): run `ml:sync-metadata` afterwards. Moved files take the
class/sub-category of their new folder (it must be one of the folders above); deleted files are recorded as rejected,
so the collector never downloads them again.

Sources: Wikimedia Commons, English Wikipedia, and two Hugging Face datasets (`--sources` selects them). Why other
sources are not automated: `docs/research/IMAGE-SOURCES-RESEARCH.md`. Set `HYRULE_COLLECTOR_CONTACT` (your e-mail
or a URL) to identify yourself to Wikimedia and get a 20× higher rate limit.

## Importing images by hand (Google Images, Spriters Resource, your screenshots…)

1. Select the images in your browser downloads or Explorer and **drag them** into the right folder, e.g.
   `data/inbox/zelda/twilight-princess/`. Several folders at once are fine. Sprite sheets go to
   `data/inbox/sprite-sheets/<label>/<subcategory>/` and are cut into one image per sprite.
2. Run `npm run ml:import-images` (from WSL). Everything is imported in one go.

Or skip the folders: `npm run ml:import-images -- --label zelda --subcategory twilight-princess` and drag the files
from Explorer into the terminal to paste their paths (add `--sprites` for sprite sheets, `--dry-run` to preview).

Each image is validated (real JPEG/PNG/WebP, not an HTML page, not corrupted, not a thumbnail), compared with every
image already in `raw/` (SHA-256 + perceptual hash), renamed `<label>-<subcategory>-<original name or "manual-import">-<hash>.<ext>`
and recorded in `sources.json`. Only known facts are recorded: the page/URL your browser saved with the file
(Windows "Zone.Identifier") and credits embedded in the image; license and author stay "unknown" otherwise.
Imported files leave the inbox; refused ones move to `data/inbox/_rejected/<reason>/`. A summary is printed and
saved to `data/metadata/imports/`.

Images are for **private study only**: they show © Nintendo characters, and many photos require attribution
(`attribution` in `sources.json`).

## Conventions

- **The folder name is the label.** An image in `raw/zelda/` is a training example whose correct answer is "zelda".
  New folders become classes automatically (see `packages/ml/src/dataset/classes.ts`); no code change needed.
- **Accepted formats:** JPEG, PNG, WebP. Any size: preprocessing resizes everything to the model's input size.
- **One subject per image.** An image showing both Link and Zelda has no single correct label and confuses training.
- **`other`** must be diverse: other Zelda-series characters, other games, people, animals, landscapes. It teaches
  the model what "neither" looks like (see `docs/concepts/01-image-classification.md`).
- **Balance:** aim for a similar number of images per class. If one class is much larger, the model can score
  well by mostly predicting that class.
- **No duplicates across splits.** The same picture (or a near copy, e.g. resized) in both `train/` and `test/`
  inflates test accuracy, because the model is tested on something it has already seen.

## Why three splits

| Split        | Used for                                          | Affects weights? |
| ------------ | ------------------------------------------------- | ---------------- |
| `train`      | Learning: gradients are computed on these images  | Yes              |
| `validation` | Watching for overfitting, tuning hyperparameters  | No               |
| `test`       | One final, unbiased estimate of real accuracy     | No               |

A typical split is 70% / 15% / 15%. The split is done **per class** (stratified) so each split keeps the same
class proportions.
